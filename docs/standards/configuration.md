# Configuration Standards

> Conventions for environment variables, secrets, build-time generated files, and local services. Astro code reads config via `import.meta.env.*`; Netlify functions (Node runtime) read `process.env`.

## Environment variables — Astro side

Astro source (`src/**`) reads configuration through `import.meta.env.*`, never `process.env`:

```ts
const site = import.meta.env.SITE_URL;         // ✅
const key  = import.meta.env.STRIPE_SECRET_KEY; // ✅ (server-side only — see below)
const key  = process.env.STRIPE_SECRET_KEY;     // ❌ in src/** — undefined in SSG output
```

`PUBLIC_`-prefixed vars are the only ones inlined into client bundles. Anything else referenced in a client island leaks nothing but also resolves to `undefined` — keep secrets in server-only modules (`src/lib/**`).

### Required variables

Full list lives in `.env.example` (shared) and `.env.local.example` (machine-local overrides): `DATABASE_URL`, `SUPABASE_*`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `STRIPE_*` (secret/publishable/webhook-secret/success-url), `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `SMTP_HOST`/`SMTP_PORT` (dev: Mailpit), `GOOGLE_CALENDAR_*` / `GOOGLE_OAUTH_*`, `SITE_URL`. See `docs/LOCAL_DEV.md` for local setup and `docs/INFRA.md` for production.

### Mocks when placeholders are set

The codebase degrades gracefully when secrets are placeholders — do not remove these guards:

- `STRIPE_SECRET_KEY=sk_test_placeholder` → Stripe mock (no real API calls).
- `GOOGLE_CALENDAR_MOCK=true` → fictional Wednesday slots instead of the real calendar.

## Environment variables — Netlify functions side

`netlify/functions/**` run in the Node runtime where `process.env` is correct. Netlify does **not** expose build-only variables (`CONTEXT`, `COMMIT_REF`) to function runtime — `scripts/generate-build-env.mjs` snapshots them at build time into `netlify/functions/_lib/build-env.ts`.

- **`netlify/functions/_lib/build-env.ts` is AUTO-GENERATED — never edit it.** It is regenerated by `predev`/`pretest`/`prebuild`/`pretypecheck` npm hooks (or `npm run generate-build-env`).

## Secrets handling

- `.env` and `.env.local` are gitignored — never commit them, never paste real values into docs or issues.
- Templates (`.env.example`, `.env.local.example`) are committed and must stay in sync when a variable is added.
- Production secrets are set with `netlify env:set` (see `docs/INFRA.md`), never through the UI alone (auditability).

## Local services (Docker)

```bash
npm run db:start   # Postgres + Mailpit
npm run db:reset   # ⚠️ destructive — drops schema, replays ONLY 001_init.sql
npm run db:stop
```

- `db:reset` is destructive **and incomplete**: after a reset, apply migrations `002`→`014` manually, in order, from `supabase/migrations/`.
- Mailpit UI (dev email capture) runs on port 8025; SMTP on 1025 via `SMTP_HOST`/`SMTP_PORT`.

## Database migrations

- Schema changes go in `supabase/migrations/*.sql`, named `NNN_description.sql`, applied in numeric order.
- Never edit an applied migration — add a new one.
- The `dev` database and the production database must both reach the same final schema; note any manual steps in the migration file header comment.

## Build & deploy configuration

- Deploy target is Netlify (`netlify.toml`); Node version is pinned in `.nvmrc` and must match `netlify.toml`.
- `npm run build` is the only supported production build; CI gates on it (`.github/workflows/ci.yml`).
- SPA legacy aliases (`/Tarifs`, `/Services`, …) are redirected in `netlify.toml` — don't recreate those routes.
