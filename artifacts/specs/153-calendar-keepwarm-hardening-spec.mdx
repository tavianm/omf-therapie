## Context

Promu depuis `artifacts/frames/153-calendar-keepwarm-hardening-frame.mdx` (F-lite, approuvé). Source amont suivie : le cadre approuvé et la revue contradictoire croisée consignée dans ce document (session 2026-09-13). Supplante #135 (écritures strictes) et #137 (Freebusy unique). Amendé après revue d'experts (R-adversarial + R-architect) puis revue du plan (2026-09-13) : état `transient` du cron, porte de marge du fall-through, fermeture de l'empoisonnement vide sur le chemin patient, classification init Blobs, **CAS updated_at intégré au périmètre, bootstrap env supprimé du runtime**.

Incident déclencheur : run `calendar-keepwarm` de 2026-09-13 02:20 — issues contradictoires intra-run sur panne transitoire PostgREST. Chemin de défaillance confirmé dans le code (`src/lib/google-calendar.ts:186-206`) et **hypothèse principale** pour l'incident (les logs ne prouvent ni le 504 sur la requête token précise ni que l'upsert a abouti) : `getPersistedOAuthClient` ignore l'erreur de fetch, bascule sur le bootstrap env `GOOGLE_OAUTH_REFRESH_TOKEN` (obsolète/révoqué) et upsert cette valeur par-dessus la ligne fraîche avant le refresh.

## Intent

Le cron `calendar-keepwarm` traite des états partagés (ligne OAuth, manual slots, busy Google) comme s'ils étaient privés à chaque branche du fan-out : une panne transitoire peut produire un diagnostic « consent revoked » fantôme et des écritures obsolètes, et la télémétrie `warmed` rapporte des calculs, pas des écritures. Pourquoi maintenant : incident réel le premier jour de production du cron fusionné (#132).

## Goal

Un run keepwarm sain utilise exactement une session OAuth, une lecture manual slots et un appel Freebusy, écrit 4 entrées cache **dont les écritures sont confirmées** ; une panne transitoire amont ne peut produire un état vide ou contradictoire, et **aucun writer — même avec une vue obsolète de la ligne token — ne peut écraser une écriture plus récente** (CAS).

## Users

- **Primaire :** le patient (disponibilités fiables sur /rendez-vous ; jamais de cache vide empoisonné, ni depuis le cron ni depuis le chemin patient).
- **Secondaire :** la thérapeute (alertes invalid_grant uniquement légitimes ; plus de re-connexion suite à corruption).
- **Tertiaire :** l'opérateur (télémétrie véridique : `written`/`failed` distingués, échecs de stage partagé identifiés comme tels).

## Expected Behavior

Déroulé d'un run sain : `keepTokenWarm()` charge la ligne token une seule fois, la rafraîchit si < 15 min de validité, persiste **avec CAS `updated_at`** (un miss = une écriture plus récente existe — relecture, log, préservation de la ligne récente), et retourne le client OAuth authentifié (`KeepwarmSession`).

**Porte de marge du fall-through** : après un échec transitoire du refresh, le statut `'ok'` n'est retourné que si le token persisté garde **> `WARMUP_MIN_TOKEN_VALIDITY_MS`** de validité — constante = seuil `eagerRefreshThresholdMillis` par défaut de google-auth-library (5 min) **+ 60 s de budget warm-up**, soit 6 min. La marge doit couvrir la latence du snapshot entre le contrôle et le Freebusy (lecture manual slots, etc.) : à 5 min + 100 ms observés au contrôle, une lecture de 500 ms suffit à repasser sous le seuil eager et à déclencher un refresh caché. Marge ≤ seuil, token expiré, ou `expiry_date` absent → `'transient'`, warm-up sauté ce run, aucune alerte. Après un refresh **réussi** → `'ok'` toujours (token frais en mémoire, CAS confirmé ou non — voir CAS).

Trois états de sortie, honnêtement classés : `'ok'` (client authentifié, warm-up procède), `'transient'` (échec de lecture de la ligne, échec de refresh avec marge insuffisante — log « transient », aucune alerte), `'auth-broken'` (définitif : ligne absente, refresh_token null, invalid_grant réel — alerte cadencée 24 h, warm-up sauté, comportement #132 inchangé).

**Bootstrap env supprimé du runtime** : plus aucun chemin runtime ne lit `GOOGLE_OAUTH_REFRESH_TOKEN`. Un échec de lecture `google_oauth_tokens` → throw typé (jamais de bascule bootstrap). Une absence de ligne (PGRST116) → `getPersistedOAuthClient` retourne `null` (non configuré) avec un warn de dépréciation si la var env existe encore (la reconnexion via `/api/admin/google-oauth` est l'unique source autoritaire ; le premier-run passe par le callback OAuth, pas par un token env). Aucune écriture de la table n'est déclenchée par un chemin de lecture.

`loadAvailabilitySnapshot()` effectue UNE lecture manual slots et UN appel Freebusy (via la session injectée) ; toute erreur (504, réseau, response-level calendar errors) est classée échec de stage partagé : aucune écriture, entrées Blobs existantes préservées, log nommant le stage. En mock mode, le snapshot saute les deux lectures. La dérivation des 4 combinaisons `{in-person, video} × {60, 90}` est pure et locale (`generateSlotsForRange` + filtre de chevauchement exporté partagé). Chaque écriture cache retourne un résultat explicite (`'written'` / `'skipped-no-store'` [mock ou hors contexte Netlify] / `'failed'` [échec d'écriture **ou d'init** du store]) ; le log final distingue `computed` / `written` / `failed`.

Chemin patient : `getAvailableSlots` convertit les erreurs response-level Freebusy en erreur typée au lieu de retourner `[]` — `/api/availability` répond 503 via son catch existant et n'écrit jamais une entrée vide ; à part cela, contrat externe inchangé.

## Data Model & Consumers

- `KeepwarmSession` — `{ status: 'ok'; oauth2Client: Auth.OAuth2Client } | { status: 'transient'; reason: string } | { status: 'auth-broken' }`. Client authentifié dans tous les cas 'ok' : valide, rafraîchi, ou fall-through avec marge > `WARMUP_MIN_TOKEN_VALIDITY_MS` (`credentials.access_token === row.access_token`, `expiry_date` peuplé).
- `AvailabilitySnapshot` — `{ manualSlots: Map<string, Set<Period>>; busyPeriods: Array<{ start: string; end: string }> }`, produit par `loadAvailabilitySnapshot(oauth2Client, startDate, endDate)` ; mock → `{∅, []}` sans I/O.
- `CacheWriteResult` — `'written' | 'skipped-no-store' | 'failed'` ; init Blobs échouée → `'failed'`.
- `filterSlotsByBusy(slots, busyPeriods)` — pur, exporté, déduplique les 3 copies.
- **CAS** — tout persist de refresh (cron `keepTokenWarm` ET `getPersistedOAuthClient` côté patient) matche `.eq('updated_at', <valeur lue>)` ; zéro ligne matchée = miss → relecture + log, la ligne récente survit, l'exécution continue sur les credentials en mémoire. Pas de migration : `updated_at` existant suffit.

## Success Criteria

- [ ] **SC1 — Intégrité de lecture de la ligne token** : un échec de lecture `google_oauth_tokens` (réseau, 5xx, timeout) fait throw une erreur transitoire typée et n'exécute aucune écriture ; l'absence de ligne (PGRST116) retourne `null` **sans bootstrap env ni écriture** (warn de dépréciation si `GOOGLE_OAUTH_REFRESH_TOKEN` existe encore).

```yaml
claim:   fail-closed
priced:  "un échec ou une absence de lecture de la ligne token ne déclenche jamais le bootstrap env ni la moindre écriture sur google_oauth_tokens"
not:     "vérifier uniquement que error est non-null après .single() / la présence d'un test nommé 'fetch-error'"
oracles: ["PostgREST 504 sur le select token → throw, zéro upsert/update", "timeout réseau sur le select token → throw, zéro écriture", "PGRST116 (0 ligne) → retourne null, zéro écriture, warn dépréciation si var env présente"]
```

- [ ] **SC2 — Session injectée, états honnêtes, porte de marge** : `keepTokenWarm` retourne un client authentifié pour `'ok'` — y compris fall-through où `client.credentials.access_token === row.access_token` avec **> `WARMUP_MIN_TOKEN_VALIDITY_MS`** (= 6 min : seuil eager 5 min + 60 s de budget warm-up) de validité restante (aucun refresh caché possible : ≤ 1 appel au endpoint token par run, mesuré au mock HTTP) ; après échec de refresh : marge > seuil → `'ok'`, marge ≤ seuil / token expiré / `expiry_date` absent → `'transient'` (warm-up sauté, aucune alerte) — cas testés aux bornes : 6 min + 1 ms → ok, 6 min → transient, 4 min → transient, expiré → transient, sans expiry → transient ; échec du select propre au cron → `'transient'` (log « transient », pas « no token row »).
- [ ] **SC3 — Budget amont** : un run sain effectue exactement 1 lecture `manual_time_slots`, 1 lecture `google_oauth_tokens`, 1 appel Freebusy (avant : 4/5/4).
- [ ] **SC4 — Équivalence de dérivation (chemin de succès)** : contre des **fixtures dorées capturées depuis l'implémentation pré-refactor** (jeux réalistes de manual slots + busy periods → 4 jeux attendus, commités en JSON, y compris semaine DST Europe/Paris 2026-10-25), horloge figée (`vi.setSystemTime`), la dérivation pure produit des jeux deep-equal ; l'équivalence ne couvre pas les chemins d'erreur.
- [ ] **SC5 — Pas d'empoisonnement, sur AUCUN writer** : une erreur response-level Freebusy ou un échec de stage partagé entraîne 0 écriture cache et la préservation des entrées existantes, côté cron et côté patient (throw typé → 503, jamais une entrée vide).

```yaml
claim:   fail-closed
priced:  "une erreur amont n'est jamais persistée comme disponibilité vide — aucune écriture Blobs n'a lieu et les entrées existantes survivent, quel que soit le writer"
not:     "retester jusqu'au succès / vérifier seulement slots.length === 0 avant écriture / couvrir uniquement le chemin keepwarm"
oracles: ["Freebusy 200 avec calendars[id].errors non vide côté cron → 0 écriture, anciennes entrées intactes", "manual_time_slots 504 → échec de stage partagé, 0 écriture, entrées intactes", "Freebusy response-level via chemin patient → 503 rendu, 0 écriture de clé, entrée existante intacte", "Freebusy réseau 500 → 0 écriture, entrées intactes"]
```

- [ ] **SC6 — Télémétrie véridique + store résilient** : `setCachedAvailability` retourne `CacheWriteResult` ; le log final rapporte `{computed, written, failed}` où `written` ne compte que des écritures confirmées ; un échec d'écriture **ou d'init** du store produit `failed ≥ 1` (≠ silence du mock) ; une init échouée est retentée à l'invocation suivante (le catch réinitialise le promise mémoïsé ; le garde mock court-circuite toujours).
- [ ] **SC7 — Chemin patient inchangé (hors suppression de l'écriture vide)** : `/api/availability` conserve clés, shape, `Cache-Control: no-store` et dégradation gracieuse ; vérifié par un nouveau mini test de contrat + suites `google-calendar` / `calendar-keepwarm` vertes sans modification de contrat.
- [ ] **SC8 — CAS sur les écritures token** : tout persist de refresh (cron et patient) est conditionné par `.eq('updated_at', <valeur lue>)` ; **un miss (PGRST116 — 0 ligne matchée) préserve la ligne récente, relit, et loggue un CAS-miss** ; **une erreur 5xx/timeout sur l'UPDATE conditionnel est une erreur infra transitoire → relecture de réconciliation, jamais présentée automatiquement comme une collision**. Jamais d'écrasement d'une écriture plus récente. Précondition vérifiée par lecture croisée : toutes les écritures de la table (callback de reconnexion, persists de refresh des deux writers) modifient systématiquement `updated_at` — une colonne `token_version` entière monotone resterait une évolution plus robuste, différée.

```yaml
claim:   authz
priced:  "un writer détenant une vue obsolète de la ligne token ne peut jamais écraser une écriture plus récente de google_oauth_tokens"
not:     "vérifier seulement la présence d'une clause WHERE id='therapist' / que l'UPDATE échoue quand la table est vide / traiter un 5xx sur l'UPDATE comme un CAS-miss"
oracles: ["cron : ligne v2 (reconnexion) écrite après lecture v1 → persist du refresh matche 0 ligne (PGRST116), v2 préservée, CAS-miss loggé", "patient : même course sur getPersistedOAuthClient → v2 préservée", "UPDATE conditionnel en 5xx/timeout → relecture de réconciliation, pas de log de collision", "le callback de reconnexion n'est jamais bloqué par un CAS concurrent"]
```

## Hors périmètre

Centralisation du cooldown d'alerte invalid_grant, `maxRuntime` Sentry, imports allégés googleapis / lazy email stack, re-filtre 24 h sur cache-hit, taxonomie complète des erreurs typées amont (seule la conversion response-level → throw entre dans ce ticket), stale-if-error grace, révision monotonic du cache, suppression du miroir `_lib/` (#136). Le CAS utilise `updated_at` existant — toute colonne `token_version` dédiée est différée.
