## Context

Promu depuis le frame [129-transport-refactor](../frames/129-transport-refactor-frame.mdx) (approuvé). Lot 1 de l'issue de suivi #129 — les autres advisories (timeout/row, Sentry, `readEnv`, déplacement pipeline, `organizerEmail`, `x-cron-secret`, bornes de tests) restent dans leurs lots.

Faits techniques vérifiés (worktree `feat/129-transport-refactor`, base c0e07dc, revue experte 3 agents) :

- L'envoi d'emails side-effects est **quintuplié** : le vrai transport `sendEmail` (`src/lib/resend.ts`) ; deux wrappers `makeSendFnWithCapture` (`reconcile-confirmations.ts:179`, `reconcile-invitations.ts:129`) ; des envois bruts `resendClient.emails.send` inline dans `send-reminders.ts` (l.235, 277) et `calendar-token-heartbeat.ts` (l.85). Ce lot traite les **deux wrappers** (pattern « capture poison ») ; les deux envois bruts (fire-and-forget, pattern différent) = lot suivant trivial une fois le seam posé.
- **Racine du duplicatat** : `SendEmailResult` n'expose que `error?: string` (`resend.ts:88-92`) — l'objet erreur Resend brut (avec `statusCode`/`name`) est avalé par `sendEmailViaResend` (l.321), donc les sweeps ne peuvent pas passer par `sendEmail` tout en classifiant poison (4xx permanent) vs retryable (429/5xx/réseau) via `isRetryableResendError`.
- **Précondition runtime cron** : `sendEmail()` lit `import.meta.env.RESEND_FROM_EMAIL`/`ADMIN_EMAIL` à l'appel (l.363-365) et `getSmtpTransport`/`getResendClient` lisent `import.meta.env.SMTP_*`/`RESEND_API_KEY` (l.37-50) — accès non gardés qui **planteraient** dans le runtime cron Node (`import.meta.env` undefined). Le patron d'accès gardé existe : `(import.meta as { env?: … }).env?.X ?? process.env.X` (`stripe.ts` post-#127, `supabase.ts`).
- **Divergences constatées entre les copies** : `lastTo` capturé seulement côté confirmations (heuristique patient-vs-thérapeute, l.180-186) ; BCC `ADMIN_EMAIL` répliqué à la main côté invitations seulement (8a84a22) ; retries/backoff et `persistThreadState` absents des deux copies ; commentaire de doc dupliqué à l'identique deux fois dans confirmations (l.132-152, 153-178). Par ailleurs `resend.ts:98-102` redéfinit localement l'interface `ResendApiError` déjà exportée par `resend-errors.ts` — le seam la dédoublonne.
- `netlify/functions/_lib/` **existe déjà** (`sentry.ts`, `logger.ts`, plus `build-env.ts` généré au build) — convention établie, ignorée par la découverte de fonctions Netlify (préfixe `_`).
- L'en-tête `X-Thread-Key` envoyé par les deux wrappers n'a **aucun consommateur** dans le repo (grep : zéro lecture hors wrappers). Le vrai modèle de threading (`email_threads` + `In-Reply-To`/`References`) est celui de `sendEmail`.
- **Couverture de tests asymétrique** : `tests/unit/reconcile-invitations.test.ts` couvre poison-escape et BCC (24 tests) ; `reconcile-confirmations` n'a **aucune suite dédiée** (seules références indirectes dans `cron-schedule-source.test.ts` et `resend-errors.test.ts`) — les tests poison côté confirmations sont **à créer** dans ce lot.

## Goal

Un seul chemin d'envoi d'emails : `sendEmail` expose l'erreur brute (`rawError`) et devient lisible en runtime cron, et les deux sweeps réduisent leurs wrappers en un adaptateur mince partagé (`_lib/send-fn.ts`) qui délègue au vrai transport — héritant de ses invariants (BCC admin, tentatives explicites, threading) au lieu de les réimplémenter. Les 4 flux concernés : **POST post-réponse** (admin), **sweep invitations** (cron 20 h), **sweep confirmations** (#98, cron 5 h), **flux patient/webhook** (déjà sur `sendEmail`, contracts inchangés).

## Users

- **Primaire** : les développeurs/mainteneurs — tout invariant transport futur se déclare une fois dans `sendEmail` et s'applique aux 4 flux.
- **Secondaire** : la thérapeute (copies BCC fiables sur les flux de rattrapage) et les patientes (threading correct des conversations email quel que soit le chemin d'émission).

## Expected Behavior

1. **Seam `SendEmailResult.rawError`** — champ optionnel typé `ResendApiError` **importé depuis `src/lib/resend-errors.ts`** (supprime la redéfinition locale `resend.ts:98-102`), rempli sur tout échec API Resend (4xx/429/5xx et exception réseau : `{ name: 'network_error', message }`). Contrat **additif** : les consommateurs existants (`error?: string`) sont inchangés. Le chemin SMTP (dev) laisse `rawError` undefined (erreur nodemailer, hors classification Resend).
2. **Seam `sendEmail(params, opts?)`** — option `maxAttempts?: number` (sémantique : **nombre total d'essais** ; défaut **3** = statu quo POST/flux patient, cf. `maxAttempts` interne `resend.ts:292`). `maxAttempts: 1` = un seul essai, aucun backoff. Les sweeps passent `1` : sémantique actuelle préservée (pas d'intra-row retry, la cadence horaire ré-essaie). L'option ne s'applique qu'au chemin Resend (`sendEmailViaSMTP` n'a pas de boucle).
3. **Env-agnostique** — toutes les lectures env de `resend.ts` passent en accès gardé `import.meta.env?.X ?? process.env.X` (RESEND_API_KEY, RESEND_FROM_EMAIL, ADMIN_EMAIL, SMTP_HOST, SMTP_PORT). Aucun crash d'import/appel en runtime Node pur.
4. **Adaptateur partagé `netlify/functions/_lib/send-fn.ts`** — exporte `makeSendFnWithCapture(opts?: { maxAttempts?: number })` (nom conservé, demeure unique) → `{ sendFn, state }`. `state.lastTo` est assigné et `state.lastError` reset **avant** délégation (un throw résiduel ne laisse pas de `lastTo` stale faussant l'heuristique) ; puis `sendFn` délègue à `sendEmail(params, { maxAttempts: opts.maxAttempts ?? 1 })` et `state.lastError ← result.rawError ?? null`. Transmission de **tous** les params à l'identique (`to`, `bcc`, `subject`, `react`, `replyTo`, `threadKey`, `idempotencyKey`). Zéro protocole réimplémenté : plus de client Resend local, plus de résolution `fromEmail` locale, plus de BCC répliqué.
5. **Migration des deux sweeps** — `reconcile-invitations.ts` et `reconcile-confirmations.ts` suppriment leur wrapper local (et le bloc BCC manuel 8a84a22 côté invitations) et importent `makeSendFnWithCapture` depuis `./_lib/send-fn`. La classification poison (`isRetryableResendError(state.lastError)`), les échappatoires (flag set-once), les clés L1, les schedules, deadlines, monitors et requêtes d'éligibilité sont **inchangés**. La validation startup (clés requises) reste.
6. **Deltas voulus** (conséquences de l'unification, assumés) : (a) *threading unifié* — les sweeps créent/mettent à jour la racine `email_threads` et envoient `In-Reply-To`/`References` comme le POST : la racine existe quel que soit le premier émetteur (l'en-tête mort `X-Thread-Key` disparaît) ; (b) *BCC admin hérité* — côté confirmations, l'email patient du sweep BCC désormais `ADMIN_EMAIL` via `sendEmail` (parité avec le POST, achève la correction 8a84a22, dédup admin déjà gérée) ; (c) *SMTP dev* — avec `SMTP_HOST` défini, les sweeps envoient via Mailpit comme le reste du site (la validation startup `RESEND_API_KEY` reste requise — une clé placeholder suffit en dev).
7. **Non-deltas** — `SendEmailParams` inchangé ; aucune requête SQL, schedule, migration ou variable d'environnement nouvelle (`RESEND_FROM_EMAIL`/`ADMIN_EMAIL` figurent déjà en commentaires dashboard dans `netlify.toml`, aucune var à ajouter) ; `send-reminders.ts` et `calendar-token-heartbeat.ts` non touchés (lot suivant). **Note de latence** : le threading unifié ajoute ~2 allers-retours Supabase par email (`loadThreadState` + persist) dans la boucle bornée à 8,5 s — `deadlineHit` surviendra un peu plus tôt sur les gros batchs, le guard `DEADLINE_MS` (inchangé) garantit la correction ; les rows différés passent au sweep suivant.

**Edge cases & stratégies :**

| Cas | Stratégie |
|---|---|
| Erreur de rendu `react` (hors API Resend) | `rawError` absent → `state.lastError` null → row compté failed sans poison → re-essai passage suivant (parité comportement actuel) |
| `statusCode` absent de l'erreur Resend | `isRetryableResendError` classe en retryable (`resend-errors.ts:33-40`) → passage suivant |
| Racine thread déjà créée par le POST concurrent | `persistThreadState` fait load-then-insert/update (pas d'upsert SQL) : en séquentiel, `loadThreadState` lit la racine commise → update ; en concurrence vraie, le second INSERT viole la PK `thread_key` (migration 002) → erreur loggée non fatale, pas de doublon, email couvert par la dédup L1 |
| Throw résiduel dans `sendEmail` (hors try/catch internes) | `state.lastTo`/`lastError` assignés avant délégation → l'heuristique ne lit jamais un état stale ; l'exception remonte à la boucle sweep (isolation par row) |
| `SMTP_HOST` défini en prod cron (misconfig) | Comportement identique au runtime web (même cause racine) — pas de garde spécifique dans ce lot |
| `RESEND_API_KEY` absente au runtime | Résultat failure + log existant `[resend] Resend client non initialisé` — l'early-abort startup des sweeps reste la première ligne de défense |
