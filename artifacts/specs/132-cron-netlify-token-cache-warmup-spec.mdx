## Context

**Promoted from:** [Frame #132](../frames/132-cron-netlify-token-cache-warmup-frame.mdx)

Le trafic insuffisant du site laisse expirer les deux états dont dépend la consultation des créneaux : le token d'accès Google OAuth (~1 h de validité) et le cache de disponibilités Netlify Blobs (TTL 10 min). Le premier patient après une période d'inactivité paie le chemin complet — refresh OAuth + Freebusy + écriture cache — sur un cold start Lambda, d'où un premier chargement de plusieurs secondes.

Trois mécanismes coexistent aujourd'hui : l'heartbeat hebdomadaire `calendar-token-heartbeat.ts` (anti-révocation du refresh_token uniquement), le bouton « Reconnecter » de /mes-rdvs (palliatif des pannes #75/#113/#114), et le refresh à la volée dans `getPersistedOAuthClient` (< 5 min). Cette issue remplace le premier par un cron `*/10` qui maintient les **deux** états chauds, les deux autres mécanismes restant respectivement filet de sécurité et dernier recours.

Décision d'architecture (interview 2026-08-30) : **fusion + renommage** — `calendar-token-heartbeat.ts` est supprimé, remplacé par `calendar-keepwarm.ts`, une seule scheduled function.

## Goal

Un patient consultant les créneaux obtient une réponse < 1 s en régime normal, sans qu'aucun appel OAuth n'ait lieu dans le chemin patient, et sans intervention manuelle de la thérapeute sur 6 mois (hors révocation réelle du consentement Google).

## Users & Use Cases

- **Patient** — parcourt /rendez-vous, étape créneaux (BookingWizard → `GET /api/availability/?mode=…&duration=…&weeks=4`). Attend une réponse immédiate ; ne doit jamais subir de 503 dû à un token froid.
- **Thérapeute (admin)** — ne touche plus au bouton « Reconnecter » en régime normal ; reçoit un e-mail d'alerte uniquement si le consentement Google est révoqué (`invalid_grant`).
- **Ops (implicite)** — un seul cron à opérer, monitoré Sentry (missed-run détecté).

## Expected Behavior

### Happy path — cycle du cron (toutes les 10 minutes)

1. **Validation d'environnement** — vars requises lues via `process.env` : `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `GOOGLE_CALENDAR_ID`, `SUPABASE_DATABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (+ `ADMIN_EMAIL`, `RESEND_API_KEY` pour l'alerte N4 ; fallbacks : `GOOGLE_OAUTH_REDIRECT_URI`, `SITE_URL`, `RESEND_FROM_EMAIL`, `PUBLIC_SENTRY_DSN` optionnel). Si une requise manque : log warn + return (silencieux, comme le heartbeat actuel) — notamment `GOOGLE_CALENDAR_ID`, dont l'absence ferait échouer les 4 clés à chaque run.
2. **Lecture du token** — ligne `google_oauth_tokens` (`id='therapist'`). Absente → log warn "Connect Google Calendar first" + return. `refresh_token` absent/vide (colonne `NOT NULL` — garde défensive) → alerte e-mail admin + return.
3. **Refresh conditionnel** — si `expiry_date − now < 15 min` : `refreshAccessToken()`, persistance `{access_token, refresh_token tourné si fourni, expiry_date, updated_at}`. Sinon : skip (token assez frais).
4. **Warm-up du cache** — pour chacune des 4 combinaisons `{in-person, video} × {60, 90}` :
   - `key = buildAvailabilityCacheKey(mode, duration, 4, new Date())` (module `src/lib/calendar-cache.ts` réutilisé tel quel) ;
   - `slots = getAvailableSlots(now, now + 4 semaines, duration, mode, [])` (réutilisation directe — les modules `google-calendar.ts` et `supabase.ts` gèrent déjà le fallback `process.env`, pattern #126/T12) ;
   - `setCachedAvailability(key, slots, 900)` — TTL 15 min, garantissant le recouvrement entre deux runs.
   Les 4 clés sont traitées en `Promise.allSettled` : l'échec d'une clé n'empêche pas les autres.
5. **Observabilité** — un résumé structuré par run (refresh: oui/non, clés écrites/échouées) via le logger `./_lib/logger`.

### Happy path — côté patient (inchangé, mais désormais chaud)

`/api/availability` hit sur le cache pré-rempli → filtre les occupations DB live (`filterSlotsByBusy`) → réponse 200. Aucun appel OAuth ni Freebusy. Le refresh proactif `< 5 min` de `getPersistedOAuthClient` reste en place mais ne se déclenche plus en régime nominal (le cron garantit > 5 min de validité restante avec une marge de 10 min).

### Edge cases

| Cas | Comportement attendu |
|---|---|
| `invalid_grant` au refresh | E-mail `CalendarAuthAlert` à ADMIN_EMAIL (via Resend, comme le heartbeat actuel), **skip du warm-up**, return propre. Pas de throw bruyant. |
| Échec réseau au refresh (non `invalid_grant`) | Log erreur, puis tentative de warm-up quand même — `getAvailableSlots` retombera sur le token existant s'il est encore valide ; sinon l'échec par clé est isolé par `allSettled` et capturé Sentry. |
| Échec Freebusy sur une clé | Clé isolée (`allSettled`), autres clés écrites ; erreur capturée via `captureAndFlush`. |
| Netlify Blobs indisponible | Le store résout null en interne (`setCachedAvailability` no-op) → warm-up silencieusement inopérant ; le chemin patient bascule sur le calcul direct (jamais pire qu'aujourd'hui). Détecté par la vérification post-déploiement (entrées attendues dans le store), pas par une erreur de run. |
| `GOOGLE_CALENDAR_ID` absent | Skip préventif avant le warm-up (warn) — sinon `resolveCalendarId` ferait échouer les 4 clés à chaque run (4 erreurs Sentry / 10 min). |
| Resend indisponible (alerte) | Log erreur, le run continue et se termine proprement. |
| `GOOGLE_CALENDAR_MOCK=true` (dev) | Store Blobs désactivé en mock → warm-up no-op naturel ; logs seulement. |
| Race cron ↔ patient (refresh simultané) | Deux access tokens valides émis par Google ; dernier écrivain gagne en DB ; bénin — aucun verrou nécessaire (voir Technical Decisions). |
| Patient pendant la fenêtre TTL expiré / cron pas encore passé | Miss cache → chemin complet existant (dégradation égale à l'état actuel). |
| Plus de ligne token (reconnexion jamais faite) | Warm-up sans objet : alerte + return, comme aujourd'hui. |

## Constraints

- **Littéral `schedule` inline obligatoire** dans `config` — l'extracteur statique Netlify (`@netlify/zip-it-ship-it`, `parsePrimitive`) ne résout que les `StringLiteral` ; un `Identifier` produit `schedule: null` et le cron ne se déclenque plus (régression #113). La const partagée avec Sentry reste autorisée en parallèle, mais le littéral doit être dupliqué inline.
- Runtime Node pur : `process.env` uniquement ; clients Supabase instanciés dans la fonction (précédent `reconcile-invitations`).
- `initSentry()` doit précéder `Sentry.withMonitor()` (le check-in `in_progress` porte le `monitor_config` — régression #113) ; `withMonitor` wrappé dans un vrai handler.
- Quotas : seuil 15 min observé → ~30 refresh/jour (~900/mois) ; ~4 320 invocations/mois — négligeables face aux limites Netlify (125 k) et Google.
- Vérification WSL : tests en `--maxWorkers=1` sur fichiers ciblés ; gates complets (`test:low`, lint, build) séquentiels par le lead.
- Langue : code/commentaires EN, libellés user-facing (e-mails) FR, commits FR présent.

## Non-goals

- Supprimer le refresh à la volée `< 5 min` (`getPersistedOAuthClient`) — filet de sécurité.
- Supprimer le bouton « Reconnecter » (`GoogleCalendarStatus`) — dernier recours sur révocation.
- Optimiser le cold start Lambda (bundle `googleapis`) — problème distinct.
- Pré-remplir les combinaisons `weeks ≠ 4` (l'API accepte 1–8 mais seul le wizard `weeks=4` existe) — YAGNI.
- Invalider le cache sur mutation de RDV — mécanisme existant (`invalidateAvailabilityCache`) inchangé.

## Technical Decisions

1. **Fusion + renommage** (décision interview) — une seule fonction `calendar-keepwarm` : le warm-up nécessite de toute façon un token frais ; séparer reviendrait à dupliquer le refresh. L'ancien monitor Sentry `calendar-token-heartbeat` devient orphelin — à archiver manuellement dans le dashboard Sentry (action one-shot notée dans la PR).
2. **Seuil refresh 15 min** — équilibre : ~30 refresh/jour max (loin des limites Google) tout en garantissant ≥ 5 min de validité restante au moment où un patient arrive (marge 10 min au-dessus du seuil proactif patient), donc zéro refresh dans le chemin patient.
3. **TTL warm-up 900 s vs cadence 600 s** — le recouvrement élimine la fenêtre de miss entre expiration d'une entrée et réécriture par le run suivant ; le chemin patient garde le défaut 600 s (aucun changement de comportement au miss).
4. **Warm-up sans occupations DB** — le hit patient ré-applique toujours `filterSlotsByBusy` (busy DB live) ; écrire les slots Google-only évite de figer des busy périodes dans le cache (plus sûr vis-à-vis des mutations récentes).
5. **Pas de verrou cron ↔ patient** — deux refreshs concurrents avec le même refresh_token produisent deux access tokens valides ; last-write-wins en DB, bénin. *Condition* : suppose que Google ne fait pas tourner le refresh_token à chaque échange (comportement observé actuellement). Si une politique de rotation était activée, un last-write-wins pourrait persister un refresh_token périmé — fenêtre de 10 min, probabilité faible, à reconsidérer si une alerte `invalid_grant` récurrente apparaît.
6. **`getAvailableSlots` réutilisé sans DI** — le module gère déjà `process.env` au premier accès (#126/T12) ; le seam `CalendarClientOptions` reste disponible si un jour le cron doit injecter son propre client, mais n'est pas nécessaire ici (le refresh de N2 précède et rend le token frais pour les 4 appels).

## Open Questions

- Confirmer en production que `expiry_date` retourné par Google reste ~3 600 s (si Google changeait la durée d'un access token, le seuil de 15 min resterait valable mais le compte de refresh/jour varierait — cosmétique).
- **Dette axiale (2-strikes, non bloquant)** — le flux « refresh + persistance token » existera en 2 sites après cette PR (`getPersistedOAuthClient` dans `src/lib/google-calendar.ts`, N2 dans le cron). Sous le seuil 3-strikes de l'ADR-001 ; extraire un primitif `refreshAndPersistToken()` dans le domaine calendar si un 3ᵉ consommateur apparaît. À noter aussi : `google-calendar.ts` approche le seuil de split (878 lignes / trigger 1000) — rien à faire dans cette PR (réutilisation seule).
